# T93 request-shape experiments

Task 2 adds `build.luna_provider_mode: responses | lite` in project or machine
configuration (project wins). Default: responses. Luna requests explicitly use low
text verbosity, unchanged configured reasoning effort, summary omission for none,
auto tool choice, and sequential calls. Sol shaping/planning settings are unchanged.

Lite is an opt-in Codex-backend experiment pinned to openai/codex rust-v0.160.0,
a956835d020762cb2b570053af06f643a11c0ecc (`core/src/client.rs` build_responses_request).
It moves tools and instructions to stable developer items, omits top-level tools,
uses all-turn reasoning context and disables parallel calls. IDs are deterministic
payload/session hashes; existing history IDs are preserved. The protocol header
is sent only for Lite. Originator remains kogen. No internal client metadata or
Codex identity is copied. Owned SIWC/public API credentials cannot select Lite:
the attempt fails as unsupported, without a fallback to another shape.

Every attempt journals adapter/version, verbosity, summary, reasoning context,
tool choice, parallel behavior and a stable nonsecret session ID in requests.jsonl.
Golden serialized requests and loopback tests validate wire behavior. Lite backend
availability and latency/success-rate improvements remain unmeasured: this task's
credential-access prohibition prevents authenticated A/B trials. No claim of a
latency improvement follows from synthetic tests. For a later authorized trial,
randomize responses/Lite on the same frozen task history/tools, Luna/max, account
class and concurrency; retain all failures and report the >300 s/>900 s counts.

Public controls: https://developers.openai.com/api/docs/guides/reasoning
Pinned protocol: https://github.com/openai/codex/blob/a956835d020762cb2b570053af06f643a11c0ecc/codex-rs/core/src/client.rs

Task 6 adds independent `build.tool_result_tokens` (default 2000, range 128–100000)
and optional `build.model_generation_tokens` (default absent, range 1–100000).
Project settings override machine settings. The generation cap applies to develop
requests, preserving shaping/planning configuration. A 12000-token cap is an opt-in
experiment for reasoning-heavy builders, including reasoning and visible output;
it is not a Codex parity setting. Conventional public Responses/SIWC support the
cap. Lite and unverified proprietary endpoints reject it explicitly before loading
credentials. A custom endpoint capability flag can opt into supported conventional
cap serialization. No adapter or effort is silently changed to accommodate a cap.

Every builder tool accepts `tool_result_tokens`, `output_offset` and `output_limit`.
The latter two select a zero-based UTF-8 byte range in the result; read's existing
`offset`/`limit` still select source lines. Result tokens are explicitly estimated
at four UTF-8 bytes per token, with notices included in the byte ceiling. Small
results are complete; large results preserve starts and ends with a visible notice.
The notice identifies shown half-open byte ranges and a retained-content handle.
`tool_output` retrieves missing ranges without repeating a command and is available
to shell-only and read-only stages too. Process output comes from its full run log,
not only Proc's bounded tail. Retained text is redacted, binary output is base64,
and handles cannot follow symlinks out of the run's logs. Files being written and
model-generated tool arguments are never shortened by a tool-result budget.
Scoped shaper writes honor the same advertised result ranges and leave receipts;
their complete file contents and Sol-high model selection are preserved.

`requests.jsonl` now distinguishes `record_kind=model_request` from
`record_kind=tool_result`. Model records keep timing/usage fields and independently
journal generation and default tool-result budgets in request_settings. Tool records
have no model start time or token spend: they identify call/tool, requested/effective
result budget, original retained bytes, returned bytes, shown ranges, truncation,
handle, and the byte/token estimator. Consumers counting attempts should select
model_request rows (or numeric started_at). Tool receipts are also in transcripts.
Incomplete responses retain safe response IDs/reasons and partial/unknown usage;
missing token counts stay null. No calls from an incomplete response, or items still
marked in progress in a completed envelope, execute. Reported incomplete spend is
included in attempt usage reports.
